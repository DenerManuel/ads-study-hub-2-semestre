SQL Sem Enrolação: DDL, DML, SELECT, JOINs e Subconsultas

Bora direto ao que cai na prova — linguagem simples, foco pesado em SELECT, simulador de JOINs e quiz comentado alternativa por alternativa.

1. Os 3 Grupos da SQL (DDL, DML e DQL)

Pensa no banco de dados como uma planilha organizada. Os comandos SQL se dividem em 3 grupos bem fáceis de separar na cabeça:

🏗️ DDL (Estrutura)

Cria, muda ou apaga a estrutura da tabela (o esqueleto).
Comandos: CREATE, ALTER, DROP.

✏️ DML (Dados)

Coloca, altera ou apaga as linhas lá dentro.
Comandos: INSERT, UPDATE, DELETE.

🔍 DQL (Leitura)

Só lê e busca informação sem mexer em nada.
Comando: SELECT.

⚠️
Se liga nessa armadilha

Tem professor que coloca UPDATE produtos SET preco = 10 WHERE id = 3; na prova e pergunta o grupo. Mesmo usando WHERE, continua sendo DML porque altera dado gravado!

Tipos de Dados que Você Precisa Saber

Na hora de montar o CREATE TABLE, cada coluna ganha um tipo:

Tipo Quando usar Exemplo direto
INT / SERIAL Número inteiro. No PostgreSQL, SERIAL numera sozinho (1, 2, 3…). id SERIAL PRIMARY KEY
CHAR(n) Texto de tamanho fixo. Segura zeros à esquerda! cpf CHAR(11) → guarda '01234567890' inteiro
VARCHAR(n) Texto que varia de tamanho até o limite n. nome VARCHAR(100)
DECIMAL(p, s) Dinheiro ou número quebrado exato. p = total de dígitos; s = casas após a vírgula. DECIMAL(10,2) → 8 dígitos antes + 2 depois (máx. 99.999.999,99)
DATE / BOOLEAN Data ('2026-02-10') e verdadeiro/falso. criado_em DATE
🪪
Por que CPF nunca é INT?

Primeiro porque você não faz conta de somar CPF. Segundo porque se o CPF começar com zero (01234567890), o INT arranca o zero da frente. Por isso CPF sempre vai em CHAR(11).

Restrições e Chave Estrangeira (FK)

  • PRIMARY KEY: RG da linha. Junta NOT NULL + UNIQUE (não pode faltar e não pode repetir).
  • NOT NULL: Campo obrigatório.
  • UNIQUE: Não deixa cadastrar repetido (ex.: email ou CPF).
  • CHECK (...): Trava de segurança (ex.: CHECK (salario >= 1000)).
  • DEFAULT valor: Se você não mandar nada no INSERT, o banco preenche sozinho (ex.: estoque INT DEFAULT 0).
  • FOREIGN KEY: Amarra uma tabela na outra. Impede cadastrar um pedido para um cliente que nem existe.

E se eu tentar apagar o "pai" que tem "filhos"? (ON DELETE)

  • Sem nada (padrão / RESTRICT / NO ACTION): O banco trava e dá erro. Não deixa apagar cliente com pedido.
  • ON DELETE CASCADE: Apagou o cliente? O banco passa o rodo e apaga os pedidos dele junto.
  • ON DELETE SET NULL: Apagou o cliente? Os pedidos ficam, mas o id_cliente deles vira NULL. Detalhe: se a coluna tiver NOT NULL, dá conflito e erro!

INSERT, UPDATE e DELETE sem Mistério

📌
Regra do INSERT

O número de colunas e o número de valores em VALUES têm que bater certinho, na mesma ordem. Declarou 4 colunas e mandou 3 valores? Erro na hora. 

-- Inserindo registro
INSERT INTO funcionarios (nome, cargo) VALUES ('Maria', 'Gerente');

-- Alterando só quem interessa (NUNCA esqueça o WHERE)
UPDATE funcionarios SET salario = salario * 1.10 WHERE departamento_id = 10;

-- Apagando linhas específicas
DELETE FROM funcionarios WHERE departamento_id = 20;
💣
Cuidado mortal no UPDATE e DELETE

Se você rodar UPDATE funcionarios SET cargo = 'Analista'; sem WHERE, o banco não reclama: ele muda a tabela inteira! E no DELETE FROM funcionarios; sem WHERE, ele apaga todas as linhas, mas a tabela vazia continua existindo no banco.

Transações: BEGIN, COMMIT e ROLLBACK

Transação é um pacote de "ou vai tudo, ou não vai nada". Pense numa transferência Pix: tira R$ 100 da conta 1 e bota R$ 100 na conta 2.

💸
Os 3 comandos da transação

• BEGIN; → Abre o rascunho seguro.
• COMMIT; → Bate o martelo e salva tudo no banco.
• ROLLBACK; → Deu ruim ou desistiu? Volta tudo exatamente como estava antes do BEGIN!

O Coração da Prova: Ordem do SELECT

No SQL você é obrigado a escrever as cláusulas nessa ordem exata. Se inverter WHERE com FROM, ou HAVING com GROUP BY, o banco barra na hora: 

SELECT   colunas          -- 5º: escolhe o que mostrar na tela
FROM     tabela           -- 1º: abre a tabela
WHERE    filtro_linhas    -- 2º: filtra linha por linha
GROUP BY colunas_grupo    -- 3º: junta em grupos
HAVING   filtro_grupos    -- 4º: filtra os grupos prontos
ORDER BY colunas_ordem;   -- 6º: ordena a resposta final
💡
Conta no SELECT não muda a tabela

Se você fizer SELECT nome, salario + 500 AS ajustado FROM funcionarios;, isso só faz a conta pra exibir na tela. Lá no banco, o salário continua igualzinho.

Filtros do WHERE que Mais Caem

Operador O que faz Ponto de atenção
BETWEEN a AND b Pega valores entre a e b. Inclui as pontas! (3000 AND 5000 pega 3000 e 5000).
IN (a, b, c) Checa se está dentro da lista. Muito mais limpo que vários OR.
LIKE / ILIKE Busca pedaço de texto.
% = qualquer coisa (0 ou mais letras).
_ = 1 letra exata. 		No PostgreSQL: LIKE diferencia maiúscula de minúscula; ILIKE ignora!
IS NULL Acha campos vazios (nulos). Nunca escreva = NULL! Isso sempre dá falso e retorna 0 linhas.
⚠️
AND sempre fura a fila do OR!

Igual na matemática (vezes antes de mais), o SQL resolve AND antes de OR.
Em WHERE cargo = 'Gerente' OR cargo = 'Analista' AND salario > 5500, o banco entende: cargo = 'Gerente' OR (cargo = 'Analista' AND salario > 5500). Quer mudar a ordem? Bote parênteses!

Funções Agregadas (Resumindo Linhas)

Elas pegam várias linhas e devolvem um número só:

  • COUNT(*): Conta todas as linhas da tabela (até quem tem campo vazio).
  • COUNT(coluna): Conta só onde aquela coluna não é NULL!
  • SUM(col): Soma tudo.
  • AVG(col): Faz a média.
  • MAX(col) / MIN(col): Pega o maior e o menor valor.
📦
Como pensar no GROUP BY

Imagina separar as fichas dos funcionários em montinhos na mesa por departamento: um monte pro dept 10, um pro 20 e um monte separado pra quem tem NULL. Depois, o COUNT ou AVG faz a conta dentro de cada montinho.

WHERE × HAVING (E a Trava do PostgreSQL)

WHERE

Filtra linha por linha antes de montar os grupos. Não aceita AVG(), SUM() nem COUNT().

HAVING

Filtra os grupos já prontos depois do GROUP BY. É aqui que vai HAVING AVG(salario) > 4000.

⚠️
Erro clássico de SELECT + GROUP BY

SELECT departamento_id, nome, COUNT(*) FROM funcionarios GROUP BY departamento_id;
Isso dá erro no PostgreSQL! Se você agrupou por departamento, tem várias pessoas dentro do mesmo grupo — o banco não adivinha qual nome mostrar. Toda coluna solta no SELECT tem que estar no GROUP BY.

JOINs: Colando Duas Tabelas Lado a Lado

Os dados ficam separados em tabelas (ex.: clientes e pedidos). O JOIN junta as duas usando o campo que liga uma na outra (PK com FK).

Tipo de JOIN Quem aparece no resultado?
INNER JOIN Só quem deu match dos dois lados. Quem ficou sozinho some.
LEFT JOIN Traz todo mundo da esquerda. Se não tiver par na direita, completa com NULL.
RIGHT JOIN Traz todo mundo da direita. Se não tiver par na esquerda, completa com NULL.
FULL OUTER JOIN Traz todo mundo dos dois lados, botando NULL onde faltar par.
CROSS JOIN Cruza cada linha de uma tabela com todas da outra (4 × 4 = 16 linhas). Sem ON.
💡
2 macetes que salvam questão

1. Coluna com nome repetido: Se as duas tabelas têm coluna nome, você é obrigado a dizer de qual é (f.nome, d.nome), senão dá erro de ambiguidade.
2. Achar quem NÃO tem pedido: Faz um LEFT JOIN de clientes com pedidos e bota WHERE pedidos.produto IS NULL!

Subconsultas (Um SELECT Dentro de Outro)

Sem segredo: é um SELECT entre parênteses dentro de outro comando. O banco sempre resolve o de dentro primeiro e joga a resposta pro de fora.

1. Devolve 1 único valor (Escalar)

Vai com =, >, <.
Ex.: WHERE salario > (SELECT AVG(salario) FROM funcionarios)

2. Devolve uma lista (Várias linhas)

Vai com IN ou NOT IN.
Ex.: WHERE id IN (SELECT cliente_id FROM pedidos)

⚠️
Erro clássico: usar = com várias linhas

WHERE id = (SELECT cliente_id FROM pedidos) dá erro! O sinal de = só aceita 1 valor. Quando a subconsulta devolve várias linhas, tem que usar IN.

Diferença prática: IN × INNER JOIN

Se o Bruno fez 2 pedidos:
• No WHERE id IN (SELECT cliente_id FROM pedidos), o Bruno aparece 1 vez só (estamos só filtrando a tabela clientes).
• No INNER JOIN pedidos, o Bruno aparece 2 vezes (uma linha para cada pedido dele).

Exemplo A — COUNT(*) × COUNT(departamento_id)

SELECT COUNT(*), COUNT(departamento_id) FROM funcionarios;

Resposta: 6 e 5. O COUNT(*) conta todas as 6 linhas; já COUNT(departamento_id) pula o Hugo porque o departamento dele é NULL.

Exemplo B — GROUP BY + HAVING

SELECT departamento_id, AVG(salario) AS media
FROM funcionarios
GROUP BY departamento_id
HAVING AVG(salario) > 4000;

Passo a passo na mão:
• Dept 10: (3000 + 6000) / 2 = 4500.00 → passa no HAVING!
• Dept 20: (3500 + 2000 + 5000) / 3 = 3500.00 → cai fora.
• Dept NULL: 1200.00 → cai fora.
Resultado: Só volta 10 | 4500.00.

Subconsultas na Prática

1. Quem ganha acima da média?

SELECT nome, salario
FROM funcionarios
WHERE salario > (SELECT AVG(salario) FROM funcionarios);

Como o banco pensa:
1º) Resolve o parêntese: soma 20.700 ÷ 6 = 3450.00.
2º) Fica WHERE salario > 3450.00.
3º) Traz Bruno (6000), Carla (3500) e Elisa (5000).

2. Quem não fez nenhum pedido? (NOT IN)

SELECT nome FROM clientes
WHERE id NOT IN (SELECT cliente_id FROM pedidos);

Como o banco pensa:
1º) A lista de dentro dá (1, 2, 5).
2º) Dos clientes (1, 2, 3, 4), quem não está nessa lista são Carla (3) e Daniel (4).

DDL e DML na Prática

Exemplo 1: DEFAULT preenchendo sozinho

CREATE TABLE produtos (
    id_produto INT PRIMARY KEY,
    nome VARCHAR(100) NOT NULL,
    preco DECIMAL(10,2) CHECK (preco >= 0),
    categoria VARCHAR(50) DEFAULT 'Geral',
    estoque INT DEFAULT 0 CHECK (estoque >= 0)
);

INSERT INTO produtos (id_produto, nome, preco) VALUES (7, 'Caneta', 2.50);

Como você não mandou categoria nem estoque, o banco preenche automaticamente com 'Geral' e 0.

Exemplo 2: ON DELETE CASCADE

-- Se pedidos tem ON DELETE CASCADE apontando para clientes:
DELETE FROM clientes WHERE id_cliente = 1;

Apagou o cliente 1? Os pedidos dele somem junto em cascata.

3. AS 6 ARMADILHAS CLÁSSICAS DE PROVA
⚠️

WHERE col = NULL retorna 0 linhas. Tem que usar IS NULL.

⚠️

AND manda antes do OR. Resolva os AND primeiro se não tiver parênteses.

⚠️

ON DELETE SET NULL não combina com NOT NULL. Se a FK for NOT NULL, dá conflito.

⚠️

GROUP BY no PostgreSQL: colocou coluna solta no SELECT fora de agregação? Ela precisa estar no GROUP BY.

⚠️

Nome repetido no JOIN: sempre indique a tabela (f.nome, d.nome).

⚠️

ROLLBACK zera tudo desde o BEGIN. E UPDATE sem WHERE altera a tabela inteira.
